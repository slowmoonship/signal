## ADR-001 双语（中英）

**背景** 站点面向公众，需覆盖中英文读者。
**决策** 路由 `/en`、`/zh`；`MetricDefinition` 的 name/description/methodology 均为 `{ en, zh }`。
**后果** 每个指标文案成本翻倍，漏一种语言会被自检清单拦下。中文需 Noto Sans SC，
且中文无 Inter 式字重变化，视觉层级需单独调（Phase 3）。

## ADR-002 先用免费数据源，预留付费适配层

**背景** 实测 Coin Metrics 免 key 接口把 `FeeTotUSD`/`RevUSD`/`NVTAdj` 等美元费用指标整族锁在 403 墙后。
**决策** MVP 只用免 key 源，原生单位为主，美元值由自抓 `PriceUSD` 换算。
`SourceAdapter` 从第一天就带 `auth: 'none' | 'apiKey'`，付费实现作为并行 adapter 存在，
仅在配置 key 时启用；指标定义带 `fallback`，付费源缺失时自动降级到免 key 源。
**后果** NVT 等经典指标不进 MVP。未配置 key 时行为与纯免 key 方案一致，不构成隐藏依赖。

## ADR-003 GitHub Actions 抓取

**背景** 抓取需要定时触发，第一版不想维护服务器。
**决策** `.github/workflows/ingest.yml`，`schedule` 日更 + `workflow_dispatch` 手动补数。
**后果** 抓取器保持宿主无关（就是一个 Node 脚本），后续迁到个人建站不用改代码。
GitHub cron 可能延迟数分钟，对日更场景无影响。

## ADR-004 日更，不做实时

**背景** 用户明确表示实时性要求不高，日更足够。
**决策** 全站每日一个快照。无轮询、无 SSE、无 WebSocket、无客户端刷新。
**后果** 这是最大的简化来源：没有数据过期竞态，页面在任意时刻都是一致的静止快照。
"更新时间"语义清晰。代价是价格等快变指标最长滞后 24h，需在页面明示。

## ADR-005 首页极简文字列表

**背景** 在 leerob 风格的两种密度中，用户选择极简文字列表（阅读器观感）。
**决策** 首页为分类 + 一行一条的指标列表，不做卡片、不做阴影、不加迷你走势图。
图表只出现在详情页，用 lightweight-charts 按需加载。
**后果** 移除了整套 sparkline 组件。首页更安静，信息密度低于专业数据终端，
但与"简洁克制"的定位一致。

## ADR-006 指标注册表即代码

**背景** 本质是一张由数据驱动的指标表；未来要加 ETH/SOL。
**决策** 每个指标是 `packages/metrics` 中的声明式定义对象，首页/详情/图表/来源链接全由它渲染。
**加 ETH/SOL 的成本 = 新增定义 + 新增 source adapter，页面层零改动。**
`packages/metrics` 是唯一事实源，三包都依赖它；web 不依赖 ingest，ingest 不感知 web。
**后果** 这是整个扩展性的唯一支点。硬编码指标列表被 CLAUDE.md 列为 bug。

## ADR-007 用 node:sqlite，不用 better-sqlite3

**背景** 原计划用 better-sqlite3，需要原生编译或预编译二进制，增加安装失败面。
**决策** 用 Node 内置 `node:sqlite`（Node 22.5+ 已提供，本机 22.23 实测可用）。
**后果** 零原生依赖，安装更稳。代价是该模块在 Node 22 上仍是实验特性（会打印警告），
API 可能在小版本间变化；若未来升级出问题，需评估迁移路径。
如需静音警告用 `NODE_OPTIONS=--no-warnings`，不要改代码绕过。

## ADR-008 自建 i18n，不用 next-intl

**背景** 只有两种语言，需要 locale 协商与切换。
**决策** 自建 middleware + 字典（约 60 行），不引入 next-intl。
**后果** 依赖更少，完全可控。代价是 hreflang、SEO alternates 需自己处理（Phase 4）。
若日后要接第三语言或需要更复杂的 locale 路由，换库的改动面仅限 middleware 一处。

## ADR-009 详情页图表手写 SVG，不用 lightweight-charts

**背景** PLAN §Phase 3 原写"详情页用 lightweight-charts"。Phase 1 实现时改成了服务端渲染的 SVG 折线图。
**背景（补充）** lightweight-charts 是 ~50 KB 的客户端库，必须 `use client` + 动态导入，
而页面是构建期静态生成的日更快照（ADR-004）——把 400 个点交给浏览器重画，
收益只有"悬停 tooltip / 缩放"两项；灰阶极简视觉下这两项本来就不该做成彩色十字线。
**决策** 图表改为服务端渲染的内联 SVG：纯函数，输入点数组，输出 `<path>` 与刻度文本。
`null` 点处断线而不是连过去（缺失不是零，见数据红线 1）。
**后果** 详情页 HTML 里就带着图，首屏无 JS 依赖，图表零客户端 JS。
代价是失去交互式缩放与 tooltip——若日后要做，接受"加回一个轻量交互层"的重做成本，
而不是现在就为两个交互项引入 50 KB 与 `use client`。
**对 ADR-005 的修正** ADR-005 中"用 lightweight-charts 按需加载"一句以本 ADR 为准。

## ADR-010 Fixture 与真实数据物理隔离

**背景** Phase 1 需要页面与图表跑起来，但此时还没有真实数据。
**决策** 三条同时生效，缺一条都不算数：
1. fixture 只能写进 `fixtures/btc`；写入路径若等于或位于 `public/data` 之下，生成器直接抛错；
2. 每份 fixture 文件带 `fixture: true`，页面读到就在顶部显示"非真实市场数据"告警条；
3. 数据目录由 `SIGNAL_DATA_DIR` 切换，页面代码路径完全相同——
   fixture 验证的就是真实数据会走的那条路径，不存在"只在假数据下能跑"的分支。
**后果** 任何人都不会把合成数据误当成真实行情发布，也不需要靠人记着"这次是假的"。
发布前只需 `npm run ingest:btc` 覆盖 `public/data`，告警条自动消失。
**延伸** fixture 的时间戳、数量级与减半计划按真实协议生成（例如流通量用真实减半表累积、
矿工收入 = 当日补贴 × 144 块），保证跨指标自洽——否则页面上的矛盾会被当成代码 bug 排查半天。

## ADR-011 主题 token 走 `:root` + 媒体查询 + `@theme inline`，不做手动切换

**背景** Phase 3 要求把散落的 `zinc-300` / `dark:text-zinc-400` 收敛成语义 token，
并保证明暗两态真正生效。第一版把两套颜色都写进 `@theme`（暗色那套嵌在媒体查询里），
构建产物里暗色块只剩 `dark:` 工具类、`--color-ink` 全局只出现一次——**暗色主题看着配了，实际永远不生效**。
**背景（续）** 另一条被否掉的方案是加手动切换开关。
**决策** 一、灰阶取值放在 `:root`，暗色覆盖放在 `@media (prefers-color-scheme: dark) { :root { … } }`，
由 `@theme inline { --color-ink: var(--ink) }` 把语义名映射到变量。
二、**不提供手动主题开关**，明暗只跟随系统。
**后果** `inline` 让工具类在运行时解析 `var(--ink)`，媒体查询覆盖才真正起作用；
代价是构建产物里工具类多一层变量间接，且 `@theme` 里**不再允许**放任何需要明暗切换的值。
不加开关则意味着不存在主题闪烁（`prefers-color-scheme` 在首帧已确定），
代价是用户不能在"我这台机器强制浅色但我偏好深色"时手动纠正——对一个日更快照站，这个代价比收益小。
若日后加开关，变量都已在 `:root` 上，只需覆盖同一批变量，不动任何组件。
`apps/web/test/theme.test.ts` 对这条有专门的守卫断言。
完整视觉规范见 `docs/DESIGN.md`。

## ADR-012 视觉红线由源码文本测试守卫，而不是渲染测试

**背景** CLAUDE.md §视觉红线此前只靠人肉 review 守着。
破防之后没有任何运行时报错，页面会静悄悄地变成"有点蓝的卡片墙"，而所有测试依然全绿。
**决策** 加 `apps/web/test/theme.test.ts`，直接读 `apps/web/src/**` 的源码文本，
断言不出现 `zinc-NNN`、`shadow*`、`gradient`、`rounded-full|2xl|3xl|xl`、Tailwind 彩色调色板类，
并断言暗色覆盖位于媒体查询的 `:root` 而非 `@theme`。
**后果** 视觉层第一次有了会红的守卫。代价是它管不了"class 用对了但位置用错了"——
本站构建期静态生成，没有浏览器运行时可挂，源码文本是唯一稳定的断言面。
若日后引入 Playwright 做视觉回归，本 ADR 以那时的渲染测试为准；两者不冲突。
守卫自身也做过变异验证（把 `text-ink` 改成 `text-zinc-900` 会立刻失败并指出文件与色阶）。

## ADR-013 依赖审计：记录风险评估，Phase 4 不做 major 升级

**背景** `npm audit` 报 5 条：2 critical（`tinypool` 原型污染 → RCE，经 `vitest` 传递）、
2 moderate（`@vitest/mocker` 路径穿越，同样经 `vitest`）、1 high（`postcss` 四个问题，经 `next` 传递）。
`npm audit fix --dry-run` 确认**没有非破坏性修复**：要清掉它们必须升 `vitest` 3 → 5 与 `next` 15 → 16。
**决策** Phase 4 不做这两个 major 升级，改为逐条评估并写进本 ADR。
**评估** 两条 critical 全部位于 `node_modules/tinypool`，只在 Vitest 的 worker 池里运行——
测试进程，不进入构建产物，也不参与任何线上请求；触发条件是攻击者能控制传给 `run()` 的
worker options，本仓库的 `vitest.config.ts` 全部为字面量，无外部输入。
`postcss` 的 high 只在构建期处理 CSS 时生效，而 CSS 全部是第一方源码，
产物里也不含 postcss。**没有一条落在运行时依赖路径上**（站点是纯静态 HTML + CSS）。
**后果** 接受"审计面板上永远有红字"这个状态，代价是失去了 `audit` 作为门禁的意义——
所以在 CI 里**不**加 `npm audit --audit-level=high`，那会天天红，且红的原因与用户无关。
若日后升级 `next` 或 `vitest` 大版本，这 5 条应当作为验收项重新核对，并顺带验证
`@theme inline` 主题结构、`next/og` 与 `node:sqlite` 三处在新版本下的行为（它们都依赖具体版本的实现细节）。

## ADR-014 定投等待期是**带假设的派生指标**，删失观测必须以类型披露而不是塞进告警字符串

**背景** 首页重构需要一个"直接回答我要等多久"的头条指标。
可选口径很多：平均等待期、中位数、最长等待期、最大回撤、Sharpe……它们对读者
意味着的事完全不同，而"最长等待期"最贴近"我现在开始定投，最坏情况下要等多久"。
选定它之后，问题变成：**这个数字有多可信**。
第一版实现把"路径上从未超过 +5% 的起始日"直接从枚举里丢掉，只在 `warnings` 里留一句中文字符串。

**背景（续）** 丢掉它们不只是少算几个样本。右删失的起始日恰恰是**最悲观**的那批观测——
它们是"投了很久还没回本"的那些。把它们剔除会让"最长等待期"显得比实际更短，
而这正是指标想表达的东西被自己悄悄美化掉了。

**决策** 一、新增派生种类 `dcaMaxWait`，在 `packages/metrics/src/types.ts` 的
`Derivation` 联合里显式建模：

```ts
| Readonly<{
    kind: 'dcaMaxWait'
    base: string
    thresholdPercent: number   // 收益率阈值（百分比）。5 = +5%
    windowDays: number         // 回测窗口长度（天）。起点日在该窗口内枚举
  }>
```

二、**删失不是一个字符串，是一个类型**。新增：

```ts
export type ObservationCoverage = {
  /** 确实在窗口内达到阈值的起始日数量 */
  included: number
  /** 右删失：在窗口内始终未达到阈值的起始日数量 */
  censored: number
}
```

`MetricSnapshot` 增加可选字段 `coverage`，SQLite 侧加 `coverage_json` 列
（并带 `ensureCoverageColumn` 迁移，因为 `CREATE TABLE IF NOT EXISTS` 对已存在的表是空操作，
CI 的缓存数据目录会让旧表原样留着）。页面（首页 hero + 详情页）都直接显示这两个数。

三、**`difference` / `percentChange` 之外的所有派生都必须自报假设**。
`derive.ts` 的头注释与 `quality.ts` 的 `checkDerivation` 都为此设卡：
`dcaMaxWait` 会校验 `windowDays ≥ 2`、`thresholdPercent > −100`（否则指标永远没有值）、
`deriveFrom` 必须包含 `base`、基准序列必须是日频（否则"第 k 天"在日历上没有意义）。

**后果** 好处是这类指标再也不能"悄悄换个算法"：换窗口、换阈值、换基准，
都会在类型层和校验层同时暴露，且删失数始终跟着值一起发布，读者能自己判断这个极值建立在多少观测上。
代价是**派生指标不再天然无假设**——`difference` 与 `percentChange` 只是把差值和百分比直接算出来，
而 `dcaMaxWait` 里嵌了"每天投 1 美元""持有小数份额""窗口前移一格就要重算"三重假设。
因此它的 `history.mayBeRevised` 必须为 `true`：同一根柱子下"哪一天开始投"这个答案，
会被后加入的数据改写。指标文案里也逐条写明了算法，而不是只给结论。

**注** `checkDerivation` 里对日频的判断刻意写成
`const frequency: unknown = def.frequency; if (frequency !== '1d')`。
`METRIC_FREQUENCIES` 今天只有 `'1d'` 一个值，直接比较会被 TypeScript 收窄成 `never`，
整条断言变成永远走不到的死代码——而它恰恰是"加入第二种频率"那一刻最该拦住人的那条。

## ADR-015 分类底色是全站唯一允许的彩色，且由 CLAUDE.md 明文授权

**背景** 首页表格要按分类分组（市场 / 链上活动 / 交易所·持仓 / 费用与区块 / 矿工·安全 / 估值·周期），
让读者一眼看出分组边界。用纯灰阶的横线也能分组，但 19 行连续横线在视觉上是一片，
"哪些行属于同一组"需要逐行数——分组信息没被编码进去。
另一方面，CLAUDE.md §视觉红线原文是"只用灰阶"，与"分组底色用淡色"直接冲突。

**决策** 一、**先改 CLAUDE.md，再实现**。CLAUDE.md 是本项目的最高约束来源，
按其自身规定"有异议先改本文件，不要绕过它"。§视觉红线 改为
"**除分类底色外只用灰阶**"，并新增 §分类底色 小节，列出三条硬约束：
色值只允许出现在 `globals.css` 的 `:root` / 暗色媒体查询里；
必须低饱和（HSL 饱和度上限 40%），且明暗两态都只做背景填充、不许改文字颜色；
只用于分组底色，涨跌与告警一律不染色。

二、色值全部锁在 `globals.css` 的 `--cat-*` token 里（明暗各一份），
由 `@theme inline` 映射成 `bg-cat-*` 工具类——与 ADR-011 的主题结构完全一致，
不走 `inline` 的话暗色态同样会失效。
组件侧只允许出现 `bg-cat-market` 这类**类名**，真实色值由
`apps/web/src/lib/categories.ts` 的 `CATEGORY_TINT` 独家持有。
该表的类型是 `Record<MetricCategory, string>` 而非索引签名：
新增一个分类时这个文件编译不过，而不是静默渲染成"没有底色的组"。

三、**三条约束全部由 `apps/web/test/theme.test.ts` 守住**（延续 ADR-012 的源码文本守卫思路）：
每个分类的 token 必须在明暗两态各出现一次；HSL 饱和度 ≤ 40% 且明度落在该态的可用区间；
每个分类都必须有对应的 `@theme inline` 映射且类名与分类名一一对应；
`CATEGORY_TINT` 的键集必须与注册表的 `METRIC_CATEGORIES` **完全一致**（从注册表读，不写死第二份）。

**后果** 读者能靠底色分辨分组，而底色被锁在"只表达分组、不表达好坏"的强度上。
饱和度 40% 的上限意味着这六个颜色在白底上几乎读成灰——这是刻意的：
一旦底色开始传递"红=危险/绿=安全"，它就在替读者下判断，
而"涨"对不同指标含义相反（矿工收入涨是好，费率涨不是），染色等于替读者做决定。
分类底色因此**只做背景填充**，不参与任何涨跌、告警、链接的着色。

## ADR-016 市场状态改为分层场景规则引擎，`unknown` 是独立结论

**背景** 首页需要一句话说明"现在市场在经历什么"。原型做法是给每个指标定义冷热阈值，
再按票数投票得出一个综合结论。审计发现四个问题，每一个都会让那句话变得没有意义：

一、`price-change-7d` 的值本身**就是**七日涨跌幅，原型又对它算了一次百分比变化，
等于把"涨了 12%"说成"相对自己的常态又涨了 12%"。
二、`exchange-netflow` 是有符号的水平量。从 +837 BTC 变成 −163 BTC，
百分比变化算出来是 −119%——与读者看到的事实正好相反，而"变化率下降"会被读成流入减弱。
三、缺数据、过期、历史不足时原型的投票会退化成"中性"。
"中性"是一个有立场的结论（"现在既不热也不冷"），而"判不了"不是；
把它俩混为一谈，等于在数据缺位时替读者下了一个最没有依据的判断（CLAUDE.md 数据红线 8）。
四、部分阈值参数与投票规则对最终结论没有任何影响，属于写下来骗人的摆设。

**决策** 规则整体重写为**特征层 + 场景层 + 判定层**三层，全部住在 `packages/metrics/src/market/`，
页面层只负责取结论显示，不持有任何"哪些指标算热"的知识。

特征层把六个维度（价格、动量、链上活动、交易所流向、费用需求、波动）标准化成同一种形状，
每条特征声明自己的 `kind`：

- `ownValue` —— 指标本身已经是变化量，**只取原值**（修问题一）。
- `signedSum` —— 有符号的水平量。**保留符号**，用绝对值去和**同样窗口长度**的历史分布比分位数，
  并额外输出 `sign` 与 `prevSign`，使过零（+→−）可被规则直接观测（修问题二）。
- `levelPercentile` / `drawdown` / `realizedVol` / `percentChange` —— 各自的标准化口径写死在声明里。

标准化一律用**分位数排名**而不是 z-score：这些量都是厚尾的，
均值和标准差会被单日异常值拖着走，分位数对它是稳健的。

场景层是约 60 条带 id 与双语句子的规则，命中条件只引用特征层。
规则显式声明 `family`（bull / bear）与 `priority`，`family` 只用于冲突判定，不参与投票（修问题四）。

判定层是纯函数 `readMarketScenario`：核心特征任一缺失 → `unknown.insufficient-evidence`；
最佳多头规则与最佳空头规则优先级差 ≤ 15 → `conflict.signals-disagree`；
否则取优先级最高的命中规则；全不命中 → `fallback.no-clear-signal`。
`unknown` 与任何一个结论是**并列的状态**，不是 `neutral` 的别名（修问题三）。

**后果** 首页那一句话背后的每个数字都能顺着 `ruleId → 特征 → 指标 → sourceTime` 追回去。
代价是规则表需要人工维护，且每加一条规则都要能被证明"打得中"——
`packages/metrics/test/market.test.ts` 里有一条遍历全部规则的用例，
任何一条永远不可能命中的规则都会让测试失败，堵住"写下来但不起作用"这条路。
规则只实现有数据支撑的那些，不为了凑数编造市场判断。

## ADR-017 全站只有一个绿色 token，且只标一个具体区间

**背景** ADR-015 授权了分类底色这一处彩色。首页价格走势图上还需要标出
"最长定投等待期对应的那一段"。同一屏里同时出现两种彩色，
读者会自动把它们归进同一个语义："绿色 = 好"。
而这段区间恰恰**不是**好消息——它是"这段最难受"，起点到首次达标之间的那段回撤。

**决策** 新增 token `--highlight`（明暗各一份），映射为 `stroke-highlight`。
与分类底色的区别写进 CLAUDE.md §高亮绿：分类底色**不做背景以外的任何事**，
高亮绿**只标一个具体区间**——起点日到首次达标日。
文案里禁止出现"绿色 = 适合定投 / 绿色 = 底部"这类说法。

色值仍然只写在 `globals.css` 的 `:root` 与暗色媒体查询里，组件只用语义工具类。
`apps/web/test/theme.test.ts` 增加四条守卫：全站只允许存在一个绿色 token；
它必须在明暗两态各出现一次并有 `@theme inline` 映射；
除 `PriceSparkline.tsx` 外任何组件都不得使用它；
文案里不得出现买入建议式的说法。

**后果** 绿色在全站有了唯一且窄的含义。风险是这条口子会长成"绿色 = 好"，
因此约束不只写在 CLAUDE.md，还写成了会失败的测试——
文案里一旦出现"适合定投 / 该买 / 底部区域 / 可以入场"，`copy.test.ts` 与 `theme.test.ts` 会同时失败。

## ADR-018 首页加"当前状态"列：全站唯一被推翻的视觉约束

**背景** ADR-015 授权了分类底色，ADR-017 把绿色收窄成一个区间，
两者都明确写着"涨跌、告警、链接一律不染色"。首页因此只剩"当前值"和"变化"，
读者看不出**任何一个指标现在处在什么位置**——20 个数字并排列着，
但"价格在近一年的高位还是低位""交易所是净流入还是净流出"这些读者真正想先知道的事，
必须逐个点进详情页才算得出来。首页读起来像一张数据库导出。

用户要求的状态列同时还推翻了另一条约束：首页白名单"恰好 11 个指标"。
11 个是上一轮为了视觉取舍砍出来的结果，被当成规格写进了测试；
本轮用户明确要求"不再坚持只有 11 个"，并给出了值得优先的检索方向。

**决策** 一、允许状态色作为**第二种**被授权的彩色，条件是它被管住：

- 四个色档 `--status-{hot,flat,cold,void}`，每档底色 + 文字色成对，
  色值只写在 `globals.css`，组件只用 `bg-status-*` 语义类（与 `--cat-*` 同款约束）；
- 底色 HSL 饱和度 ≤ 40%，与分类底色同一个上限；
- **不用绿色**——绿色已经是"最长定投等待期"，两者含义完全相反；
- 状态色**只归状态胶囊管**，`MetricTable` 里不得出现 `bg-status-*`，
  否则涨跌染色会从后门回来。

二、状态词的三个来源全部可核对，判定住在 `packages/metrics/src/status.ts`，
词表住在 `status-specs.ts`，页面层只取结论：

1. **特征分位档**——"这个数比过去多少比例的日子高"，沿用 ADR-016 的
   `BAND_LOW_MAX` / `BAND_HIGH_MIN`，让规则与页面用同一套分档；
2. **有符号量的方向**（净流入 / 净流出）——这是事实，不是评级；
3. **与价格的方向背离**——两个指标说反话时才给这个词。

分支顺序是 **背离 > 方向 > 分位**：分位是最弱的信息，只回答"比大多数日子高还是低"。

三、**`hot` 的含义到此为止。** `hot` = "这个数比过去 80% 的日子高"，
**不等于"该买"**。交易所净流入是 hot，费率拥堵也是 hot，
两者对读者的意义完全不同。词表里**刻意不出现"超买 / 超卖"**：
那是 RSI 一路传下来的技术分析用语，而本站没有 RSI，
借一个读者已经内建好的结论，而那个结论并不来自我们的计算。

四、算不出来一律 `ok:false` + "缺数据" + 原因（挂在 `title` 上），
**任何情况下不许为了让表格整齐而填"中性"**——沿用数据质量红线 8。

五、首页白名单取消数量上限，改为 `MAX_ROWS = 40` + 逐个点名。
选择标准写进代码注释：**同一组的指标必须能互相解释**。
取消 11 这个数字，是因为一条"恰好 11 个"的断言会在改了几次之后
变成"11 是对的"这个结论本身。

**后果** 首页从"数值清单"变成"能一眼扫出位置的信息表"，
而约束没有变松：新增的 11 条断言（`status.test.ts` 15 个用例 + `theme.test.ts` 6 条）
守住了词的长度、词的边界、三档是否真的打得到、背离是否真的构成、
以及"判不出来时绝不说中性"。

已知代价（不是 bug，是数据本身的性质）：`difficulty` / `recommended-fee-rate` /
`block-weight` / `pool-concentration` 来自 mempool.space 的**链尖采样**——
每次运行一个点，因此在站点跑满一年之前，它们的状态列必然是"缺数据（历史不足）"。
补法已在 `packages/ingest/src/sources/coin-metrics.ts` 探测确认：
Coin Metrics 的 `DiffMean` 免 key 可取（`DiffMean` 在免费清单里），
换源需要过 `assertContractCompatible` 并写新 ADR，因此本轮**不做**——
悄悄换源正是数据质量红线 5 要防的那件事。

## ADR-019 首页只让指标名称可点，并给"点哪都跳走"加了真实浏览器守卫

**背景** 用户在 Mac Chrome 里实际点页面时发现：**点击页面任意位置，
甚至右上角的 English 语言切换，都会跳到"矿工收入"详情页**。

原因不是代码写错了逻辑，而是**拉伸链接**这一手法在表格里失效：
上一版给指标名的 `<Link>` 加了 `after:absolute after:inset-0`，
而 `<tr>` 上有 `relative`——本意是让伪元素撑满整行。
但绝对定位的后代在表格行里的**包含块并不可靠**：伪元素以整张表（乃至整页）
为包含块铺开，于是**表格里最后一个链接的伪元素盖住了全页**。
`miner-revenue-usd` 恰好是最后一行，所以任何点击都落到它身上。

这类缺陷没有任何运行时特征：页面照常渲染、控制台一片干净、
单元测试与源码断言全绿。**只有把指针放到页面上按下去才会现形。**

**决策** 一、**第一版只有指标名称本身可点**，放弃整行可点。
表格可点的收益很小，而"点哪都跳走"的代价极大。

二、`<tr>` 不再是定位容器，表内不再出现任何绝对定位。
`homepage-ui.test.ts` 断言表内没有 `absolute` / `relative` / `after:inset-0`，
以及没有 `fixed` / `z-*` 覆盖层。

三、**新增真实浏览器测试**（`apps/web/test/browser.test.ts`）：
真的加载页面、真的点、真的看 URL 变了没有。覆盖
"点价格 → 价格详情"、"点 MVRV → MVRV 详情"、"点矿工收入 → 矿工收入详情"、
"点 English → 只切语言"、"点空白 → 不跳转"、
"链接点击区域不盖住表格之外"、"判定依据单行"、"1366 与 375 不横向溢出"、
"绿色背景带与 worstCase 一致"、"价格纵轴不出现负刻度"。

**它怎么在 CI 里不添乱**：缺浏览器或缺预览服务时**整体跳过**，
`npm run test` 仍然是自包含的（一条测试都不会红）。
想要这组断言生效，需要一个 Chromium、一个跑着的预览服务，以及 playwright-core。

四、顺带修掉三件在真实浏览器里才看得见的事：
- **375px 横向溢出 26px**：长数字（`US$1,524,281,584,722.37`）把表格的
  最小宽度撑到 381px。`break-words` 不改变最小内容宽度，
  改用 `wrap-anywhere`（`overflow-wrap: anywhere`），桌面端恢复默认。
- **判定依据换行**：把 `statusBasis` 的输出压成短版
  （`近1年 P66` / `7日净流入 1,173 BTC` / `历史不足`），
  完整原因只进 `title` 与详情页。
- **价格纵轴出现负刻度**：8% 的下边距把轴推到 −10,000 美元，
  等于宣称比特币有过负价格。非负序列的下界改取它自己的最小值。

**后果** 首页的点击行为变得可预期，且这次的行为**有真实浏览器测试兜底**。
代价是"整行可点"这个交互被放弃——如果日后要恢复，
必须先解决表格行作为绝对定位包含块的问题，并且仍然要有浏览器测试。

## ADR-020 修掉特征层的 O(n²)：冷构建从失败到 17 秒

**背景** 准备上线时发现 `npm run build` **冷启动会失败**：
`Failed to build /[locale]/page: /en after 3 attempts`，
原因是 Next.js 单页静态生成 60 秒超时。而 CI 永远是冷构建，
所以这不是偶发——**它会让 GitHub Actions 的构建随机失败**。

本地"再跑一次就好了"是假象：第二次借到了 `.next/cache` 的 webpack 缓存。

**决策** 修 `packages/metrics/src/market/features.ts` 的 `changeSeries`。
原来它对每个点调用一次 `changeAt`，而 `changeAt` **每次都重建一张
5939 条的时间戳索引表**——单是这一个特征就要重建 5939 张表，
21 个 `percentChange` 特征合计 **41.5 秒**。
改成索引建一次、查询 O(1)，整体降到 **38 毫秒**。

**计算结果逐位不变**：把旧实现（每次重建索引）与新实现并排跑，
`changeSeries` 的输出数组**逐元素相同**（0 处不一致），
最终分位也**逐个相同**（0 处不一致）。

**后果** 冷构建从"失败"变成 **17 秒**。
新增 `packages/metrics/test/perf.test.ts`：6000 点的全表必须在 5 秒内算完。
这条守卫本身也验证过——把 `changeSeries` 改回旧写法，测试立刻报出 28 秒。

**同时确立一条规矩**：性能不再靠"本地跑过了"来证明。
一个耗时 41 秒的函数，在只跑单元测试的 CI 里是全绿的，
而它在真实构建里会超时。**与渲染相关的行为要交给真实浏览器，与耗时相关的要交给时间预算。**

## ADR-021 界面收敛为中文单语言，站点根路径直接是首页

**背景** V0.1 上线前的一轮收尾：站点一直挂着 `/en` 与 `/zh` 两套界面，
页头右上角有一个 `English` 切换入口，路由是一层 `[locale]` 动态段，
`/` 由 middleware 按 `Accept-Language` 重定向到 `/en` 或 `/zh`。

三个问题：

1. **英文界面是半成品。** 指标定义里的文案确实是双语的，但页面框架的文案
   （导航、状态词、时间说明、SEO 元数据）是后补的，两种语言的质量并不对等。
2. **`/` 依赖服务端重定向。** 这对未来的 GitHub Pages 静态发布是硬伤：
   静态导出没有 middleware，域名根路径会变成 404。
3. **两套地址意味着两套内容。** 每加一个指标就要生成两份页面，
   sitemap 里还要维护 hreflang 互指——而 V0.1 根本不需要互指。

**决策**

- **对外只有中文界面。** 页面层不再有语言切换入口，`/en` 不再生成（404）。
  但**底层文案保持双语**：`packages/metrics` 的 `Localized` 仍然是 `{ en, zh }`，
  指标定义一个字都不用删。将来若要恢复英文界面，只需把 `SITE_LOCALE` 扩回去。
  为此在 `packages/metrics/src/types.ts` 里把两种概念分开：
  `LOCALES`（底层文案支持的语言）与 `SITE_LOCALE`（站点界面的语言）。
- **规范地址在站点根下**：`/` 是首页，`/metrics/<id>` 是详情页。
  根布局回到 `app/layout.tsx`（此前刻意没有它，让 `[locale]` 那一层当根布局，
  目的是让 `<html lang>` 随语言变化——只有一种语言之后这个理由不成立）。
  `<html lang="zh-CN">`。
- **`/zh` 与 `/zh/metrics/<id>` 保留为历史别名**：站外已经发出去的链接指着它们，
  不能变成 404。它们渲染完全相同的内容，`canonical` 指向规范地址，并且 `noindex`。
- **删掉 middleware**：没有语言协商，也就没有"根路径该去哪"的问题。
  `/` 直接是中文首页，静态导出后打开域名根路径就能落到首页。
- **SEO 产物同步收敛**：sitemap 只列规范地址，不再有 hreflang 互指；
  `<link rel="alternate" hreflang>` 全部删除；`og:locale` 固定 `zh_CN`。

**后果**

- 路由树少了一层动态段，也少了两份重复页面（原先 49 页，现在 48 页——
  少掉的是 18 个英文详情页与 2 张英文分享图，多出来的是 18 个中文别名页）。
- **保留了一处刻意的例外**：分享图（`opengraph-image.tsx`）上的文字仍是拉丁字母。
  `next/og` 内置字体不含中文字形，要让图上出现中文就得往构建产物里塞一套
  约 4 MB 的 CJK 字体——为一张分享图不值得。图上的 `alt` 文本是中文。
- 以后要恢复英文界面：把 `SITE_LOCALE` 扩成数组、恢复 `[locale]` 段与
  `LocaleSwitch` 组件即可，`packages/metrics` 的双语文案一直都在。

## ADR-022 市场状态卡片用底色表达方向，颜色由规则结果决定

**背景** 首页左栏那张「市场状态」卡片只给一句话，读者要读完才知道市场偏强还是偏弱。
用户要求给它加底色：改善浅绿、恶化浅红、中性灰白，并强调三条约束——
颜色不许由文案里的"上涨/下跌"决定，证据不足就保持中性，
以及"当前偏强"与"相比上一期正在改善"不是一回事。

**决策**

- **颜色来自规则的结构化结果。** `packages/metrics/src/market/` 新增 `MarketTone`
  （`improving` / `deteriorating` / `neutral`），`readMarketScenario` 把它放进 `MarketRead`。
  取值由命中的场景规则的**方向族**决定（bull → improving，bear → deteriorating，
  neutral / mixed → neutral），另有一张**写明理由的例外表**。
  页面层只把 tone 映射成 `bg-market-improving` / `bg-market-deteriorating` /
  `bg-market-neutral`，不读规则表、不匹配文案。
- **例外的理由要写出来。** 两条"交易所净流入方向反转"规则的方向族是为**冲突判定**
  服务的，而展示语义要按"代币是流向交易所还是离开交易所"来读：
  流入交易所是恶化（与同族的"净流入尖峰"一致），离开是改善。
  不写这一条，同一件事会在两条规则里一个红底一个绿底。
- **"位置"不等于"改善"。** 只有断言了**条件变化**、且判据里带时间序列比较
  （变化量、方向反转、相对自身历史的变化幅度）的规则才允许染色。
  "价格仍在近一年高位"是位置，保持中性。这条写成了测试：
  任何用到水平分位（`levelPercentile`）特征的规则，tone 必须是 `neutral`。
- **判不了、分化、冲突一律中性。** "没有数据"不是一种市场状态，
  也不能为了让卡片好看而强行染色。
- **只染这一张卡片。** 右栏指标表一个都不染——每行都染，读者会以为整张表
  在表达同一个判断。
- **独立 token。** 新增 `--market-improving` / `--market-deteriorating` /
  `--market-neutral`，明暗各一份（中性档 = `--surface`），
  走 `@theme inline` 映射为 `bg-market-*`。色值只写在 `globals.css`。
  底色饱和度与分类底色、状态色同上限（≤40%），只做背景填充，不改文字颜色。
- **CLAUDE.md 同步修订**：§视觉红线新增"市场状态卡片底色"一节，
  把原先"绿色全站只有 `--highlight` 一个 token"改成"绿色只有两个 token，
  且语义不同、不许共用"。**这是对 ADR-017 的收窄，不是否决**——
  ADR-017 成立的前提（"绿色不许泛化成一堆含义"）仍然成立，
  现在只是明确地多了第二个、且被限定死的含义。

**后果** 读者扫一眼左栏就知道方向，读那句话仍然能拿到细节。
代价是多了一套颜色要维护，且"方向"这件事第一次有了视觉表达——
因此约束必须比分类底色更严：颜色只能由 `MarketRead.tone` 决定，
且证据不足时必须是中性。新增守卫：`market.test.ts`（tone 的判定规则、
"位置不算改善"、判不了与冲突都是中性）与 `theme.test.ts`
（色值只在 `globals.css`、明暗各一份、饱和度上限、
只有 `HeroMetric.tsx` 可以用 `bg-market-*`、不给文字另配颜色）。

## ADR-023 页脚改为品牌署名 + 两个社交入口

**背景** 页脚原来写"每日一个快照。无实时数据，不轮询。"。
这句话在页脚只是复述——首页与详情页都已经把数据时效说清楚了
（更新时刻、过期横幅、单位说明）。页脚该留的是"这是谁做的"。

**决策** 页脚换成品牌署名 `slowmoonship-慢月船`，旁边两个紧凑的社交按钮：
GitHub（`https://github.com/slowmoonship`）与 X（`https://x.com/slowmoonship`）。
新窗口打开，带 `rel="noopener noreferrer"`；图标是单色的（`currentColor`），
跟着文字颜色走——彩色图标会变成全站第二套配色系统，和视觉红线打架。
桌面端与品牌名同一行，窄屏允许换行，不许横向溢出。
页脚不加广告、不加版权年份、不加其它内容。

**后果** 站点有了明确的归属，同时少了一句被复述的话。
两个链接的地址写死在 `SiteFooter.tsx` 里，并由 `homepage-ui.test.ts`
与 `browser.test.ts` 断言——它们必须指向真实账号，不许是占位地址。

## ADR-024 站点以静态导出发布到 GitHub Pages，挂在 `/signal` 子路径下

**背景** V0.1 要正式上线，部署目标是 GitHub Pages 的**项目站点**：
`https://slowmoonship.github.io/signal/`。

GitHub Pages 不运行 Node 服务——它只发静态文件。这与此前"用 `next start`
跑一个生产服务器"的假设根本冲突：Pages 上没有进程可以跑，
Next 的运行时（SSR、RSC、middleware、图片优化）一概用不上。

三条约束同时压过来：

1. **纯静态导出。** 站点是"每日抓取 → 静态生成"的日更站（ADR-004），
   本来就没有实时性需求，静态导出几乎不损失任何东西。
2. **子路径。** 项目站点挂在 `/signal` 下，不是域名根。
   少了 basePath，所有资源 URL 都会指向 `https://slowmoonship.github.io/_next/…`，
   页面能打开但**没有样式**——这类故障在本地预览时完全看不出来。
3. **不能依赖服务端重定向。** 原来 `/` 是由 middleware 按 `Accept-Language`
   重定向到 `/en` 或 `/zh` 的。静态托管没有 middleware，
   那条路在 Pages 上直接不存在。

**决策**

- `output: 'export'`，构建产物是 `apps/web/out/`。
- `basePath: '/signal'`，取自 `apps/web/src/lib/base-path.ts` 的 `BASE_PATH`，
  **next.config 与页面代码共用同一个常量**——写错了不会编译报错，
  只会让 canonical 指向一个不存在的地址。
- `trailingSlash: true`：Next 把 `/metrics/price` 导出成
  `out/metrics/price/index.html`，交给托管方按"目录 → index.html"的规则服务。
- **删掉 middleware**，`/` 直接就是中文首页。不依赖任何服务端行为，
  静态导出后打开域名根路径就能落到首页。
- **canonical / sitemap / robots 全部带 `/signal` 前缀**；
  `metadataBase` 用域名根（`https://slowmoonship.github.io`）而不是带路径的，
  否则 `new URL('/signal/…', base)` 会把 `/signal` 那段吃掉。
- `/zh` 与 `/zh/metrics/<id>` 保留为历史别名（ADR-021），
  静态导出后它们是 `out/zh/index.html` 与 `out/zh/metrics/<id>/index.html`，
  一样能被托管方服务，canonical 指向规范地址。
- **本地预览也不再用 `next start`**：输出为 export 模式时它根本跑不起来，
  而且它证明不了线上真正会跑的那件事（Pages 只发文件）。
  改为 `apps/web/scripts/preview-static.mjs` —— 一个纯 `node:http` 的静态文件
  服务器，模仿 Pages 的三条规则（子路径、目录 → index.html、找不到 → 404.html
  且状态码为 404）。浏览器测试跑的就是它。

**后果**

- 站点不再有任何服务端：没有 middleware、没有 API 路由、没有运行时数据。
  这是"日更快照"这个产品形态的直接推论。
- `apps/web/public/data/` 里多了一份 `public/data/*.json` 的**副本**，
  由 `apps/web/scripts/sync-public-data.mjs` 在构建前同步。
  目的是让原始 JSON 也能在 `/signal/data/*.json` 上公开下载
  （robots.txt 里那条 `disallow: /data/` 就是冲它去的）。
  副本不入库——同一份数据存两处迟早分叉，而分叉的那份正好是站点用的那份。
- 分享图（`opengraph-image.tsx`）在 export 模式下必须显式
  `export const dynamic = 'force-static'`，否则构建期直接报错。
- **页面里所有链接都带尾斜杠**（`/signal/metrics/price/`）。
  静态托管对"目录但没有尾斜杠"的处理各不相同，链接一律带斜杠最稳。

## ADR-025 跨运行的历史靠仓库里的 `public/data/*.json` 合并留存

**背景** GitHub Actions 每次运行都是一台**全新**的 runner：
本地 SQLite 库是空的，"增量起点"因此永远是 null，
适配器只能按源当下能给的窗口返回数据。

这对两类源的结果完全不同：

- **Coin Metrics**：社区层给完整历史（价格回到 2010-07-18），
  每天全量取一遍，文件内容基本不变，只多了今天那一个点。
- **blockstream / mempool.space**：只提供近期数据
  （难度、推荐费率、区块权重、矿池份额都是"每天采一次样"）。
  全量取也只有最近几个点。

如果发布时直接用库里那份去覆盖已发布的文件，第二类指标的历史就会
**越写越短**（源那边每天都在往前滚，昨天发布过的点本来是可以留下来的），
更糟的是：某天源挂了，库里没有新点，
那一份文件会被写成"零个点"——指标在页面上直接变成空白。

**决策**

- **发布 = 合并，不是覆盖。** 新增 `packages/ingest/src/publish/merge.ts`：
  时间戳按 UTC 对齐去重；新值非 null 时用新值（源可以重述历史）；
  新值是 null 而旧值有效时**保留旧值**；只存在于旧文件里的点全部保留。
- **抓取失败时保持上一份数据不动**，只把它标成 stale 并写明失败原因。
  空库起跑时库里没有 meta 可标，所以这一步必须由发布环节兜住。
- **合并后没有任何有效数据点就不发布**——宁可不更新，也不能把指标清空。
- 历史因此留在**仓库里**：`public/data/*.json` 被 workflow 提交回 main，
  下一轮的合并就是拿它当"上一份"。GitHub Actions 的 cache 不承担这件事
  （cache 有配额、会过期、也可能被清；它不是数据库）。
- 数据用默认的 `GITHUB_TOKEN` 推送：**由 GITHUB_TOKEN 产生的推送不会再触发
  workflow run**（GitHub 的既定行为），所以"推送数据"不会引发新一轮采集。
  这条链路能闭环，靠的就是这一点。
- 另加一道发布物体检（`npm run data:verify`）：每个注册指标都必须有一份文件，
  且至少有一个有效数据点，且发布目录里没有注册表之外的文件。
  部署之前跑这一道，拦住"少了几个指标"的半成品。

**后果**

- 源只提供近期数据的几个指标，历史从发布当天起**逐日累积**，
  而不是永远停在"最近几天"。
- 源挂掉的那天，页面继续显示上一份有效数据并标"待更新"，
  而不是变成空白（CLAUDE.md 红线 2 的执行点从"库里"移到了"发布时"）。
- 仓库因此每天多一个数据提交。这是"历史存在版本控制里"的代价，
  也是它换来"任何一次提交都能还原出当天的站点内容"的好处。

## ADR-026 数据许可与署名跟着数据走

**背景** 本站把各来源的公开数据重新发布成 JSON，并挂在自己的域名下——
这是**再分发**。发布前必须逐个确认来源的条款：

| 来源 | 条款 | 结论 |
|---|---|---|
| Coin Metrics 社区 API | CC BY-NC 4.0，免 key，10 请求 / 6 秒 / IP | 允许非商业使用；**必须署名 + 标明许可 + 链接许可全文** |
| mempool.space REST API | 公开接口，速率限制（超限 429，反复超限可能被封），无公开许可条款 | 可用；未声明许可，注明"未公开声明" |
| blockstream.info（Esplora） | Esplora 软件为 MIT；数据是比特币公开账本 | 可用；无署名要求 |

**决策**

- 许可信息**跟着数据走**：`SourceRef` 增加可选的 `license`（名称、链接、
  使用限制说明），由适配器在 `sourceRef()` 里给出，
  于是它会出现在发布出去的 JSON 里，也会出现在详情页的"数据来源"块里。
  只写在某个 Markdown 文件里是不够的——读者下载那份 JSON 时看不到。
- 详情页在每个来源下面显示"许可：<名称>"（可点击）与限制说明。
- **非商业用途这件事要一直成立。** 本站免费、不售卖、不含付费内容，
  属于 CC BY-NC 里的非商业使用。
  **若本站将来开始商业化，Coin Metrics 社区数据必须换成付费档**
  （ADR-002 已预留付费适配器的位置），否则就是违反许可。
- 没有声明许可的来源不补一个"看起来像许可"的东西：
  `license` 缺省就表示"上游没有公开声明"，页面不显示许可行。

**后果**

- 公开的 JSON 里带着许可与署名要求，再分发这件事本身是合规的。
- 页面多了一行许可信息（在"数据来源"块内），不影响任何视觉红线。
- 商业化变成一个**被许可挡住的决策**：想做下去，先买数据源。
